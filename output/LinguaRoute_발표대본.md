## 슬라이드 4. 서비스 개요

[화면: B2B2E 이용 구조]

기업 외국어교육은 강의를 제공하는 것만으로 끝나지 않습니다. 기업 관리자는 구독·좌석·직원 진도를 각각 관리해야 하고, 직원은 수많은 강의 중 자신의 업무에 필요한 과정을 직접 찾아야 합니다.

LinguaRoute는 이렇게 흩어진 교육 운영과 학습 과정을 하나로 연결한 B2B2E 외국어교육 구독 서비스입니다.

플랫폼 관리자가 강의와 차시를 운영하고, 기업이 월간 또는 연간 요금제와 좌석 수를 선택합니다. 기업 관리자가 직원을 초대하면, 직원은 강의를 탐색하고 수강하며 진도를 쌓습니다.

이때 구독이 비활성이거나 남은 좌석이 없으면 신규 직원 가입과 수강신청을 차단해 계약 범위를 유지합니다.

## 슬라이드 7. Pain Point와 제공 가치

[화면: 이해관계자별 불편과 해결 가치 표]

기업 관리자는 직원 계정과 계약 인원을 일일이 관리하기 어렵고, 결제와 학습 현황이 흩어져 있어 교육 성과를 파악하기 어렵습니다. LinguaRoute는 초대코드와 좌석 한도, 구독·결제 정보, 직원별 진도율을 하나의 흐름으로 연결합니다.

직원은 일반 회화 강의만으로 해외 고객 미팅이나 업무 발표 같은 실제 직무 상황과 산업별 전문용어를 익히기 어렵습니다. LinguaRoute는 직무·상황·목표를 함께 분석하고, 왜 이 강의가 업무에 맞는지 추천 이유까지 제시합니다.

플랫폼 관리자는 분산된 운영 데이터와 비활성 강의 노출 위험을 관리해야 합니다. 이를 통합 운영 조회와 강의의 ACTIVE·INACTIVE 상태 관리로 해결합니다.

## 슬라이드 8. Pain Point에서 기능으로의 연결

[화면: 세 가지 핵심 Pain Point와 검증 규칙]

가장 핵심적인 세 문제는 실제 기능과 검증 규칙으로 연결했습니다.

계약 인원 초과 문제는 `user-service`와 `payment-service`가 구독 활성 상태와 남은 좌석을 검증해 차단합니다. 일반 강의로는 해결하기 어려운 직무·도메인 언어 문제는 `recommend-service`가 비즈니스 상황과 자연어 목표를 분석하고, `course-service`가 실제 ACTIVE 강의인지 다시 확인해 해결합니다. 진도 파악 문제는 `enrollment-service`가 완료한 필수 차시 수를 기준으로 진도율을 직접 계산해 해결합니다.

즉, 화면의 값을 클라이언트가 임의로 결정하지 않고 각 도메인 서비스가 검증합니다.

[화면: 5개 도메인 서비스와 Vue 기능 맵]

전체 기능은 도메인 책임에 따라 나누었습니다.

`user-service`는 기업·회원·초대·좌석과 이용 권한을, `course-service`는 강의·차시·검색·상태를 담당합니다. `enrollment-service`는 수강신청·차시 학습·진도율을, `payment-service`는 요금제·구독·결제와 상태 이벤트를 소유합니다. `recommend-service`는 조건 기반 AI 추천과 추천 결과 저장을 담당합니다.

Vue 프론트엔드는 사용자 역할별 화면을 제공하고, 모든 요청을 API Gateway의 단일 경로로 전달합니다.

## 슬라이드 11. AI 강의 추천 파이프라인

[화면: 조건 입력부터 결과 반환까지의 5단계]

AI 추천은 다섯 단계로 진행됩니다.

직원이 언어·수준·직무·상황과 “제품 사양과 기술 용어를 해외 고객에게 설명하고 싶다” 같은 목표를 입력하면 `recommend-service`가 강의 후보와 요청 조건을 구성합니다. MVP에서는 산업 도메인을 별도 코드로 고정하지 않고 이 자연어 목표와 강의 설명을 연결합니다. 이후 선택된 Provider가 후보 강의와 추천 이유를 만들고, 서버는 그 결과를 `course-service`의 실제 강의와 대조해 ACTIVE 상태와 언어 일치 여부를 검증한 후 반환합니다.

로컬 기본 환경에서는 Local Provider가 동작하고, API 키가 설정된 환경에서는 OpenAI Provider를 사용합니다. Provider 실패 시에는 `RULE_BASED_FALLBACK`으로 전환합니다. 따라서 응답의 `source=AI`는 항상 외부 OpenAI 호출을 의미하는 것은 아닙니다.

## 슬라이드 12. AI의 역할과 시스템 경계

[화면: AI가 하는 일·하지 않는 일·3중 안전장치]

추천의 신뢰성을 위해 AI와 도메인 서버의 책임을 분리했습니다.

Provider는 주어진 후보 안에서 직무·비즈니스 상황·전문용어 학습 목표와의 적합도를 판단해 순위를 정하고 추천 이유를 작성합니다. 반면 강의의 존재와 활성 상태, 수강 권한, 결제·좌석, 진도율 같은 사항은 AI가 결정하지 않고 각 도메인 서버가 검증합니다.

특히 추천 결과는 실제 ACTIVE 강의인지, 요청 언어와 일치하는지를 재검증합니다. Provider가 실패해도 규칙 기반 대체 추천으로 학습 흐름을 유지합니다.

## 슬라이드 17. LinguaRoute MSA 전체 구성

[화면: Vue·Gateway·5개 도메인 서비스·Auth·Eureka·Kafka·MariaDB]

프론트엔드는 각 서비스를 직접 호출하지 않고 `localhost:8080`의 API Gateway만 호출합니다. Auth Server가 OAuth2 Authorization Code 방식으로 Access Token을 발급하고, Gateway와 보호 API가 토큰과 최신 비즈니스 권한을 검증합니다. Eureka는 실행 중인 서비스의 위치를 등록합니다.

도메인은 `user`, `course`, `enrollment`, `payment`, `recommend` 다섯 서비스로 나누어져 있습니다. 결제·구독 상태는 Kafka로 전파하고, AI 추천은 환경 설정에 따라 외부 LLM API를 사용할 수 있습니다.

데이터베이스는 MariaDB 인스턴스와 `lecture_db`를 하나만 사용하지만, 각 서비스는 자신의 테이블만 접근하고 서비스 간 직접 조인을 하지 않습니다.

## 슬라이드 18. 서비스 책임과 데이터 소유권

[화면: 서비스별 책임·소유 테이블·연결 관계]

이 표는 서비스별 책임과 소유 데이터를 보여줍니다.

`user-service`는 기업·회원·좌석·이용 권한을 소유하고 구독 이벤트를 소비합니다. `course-service`는 강의와 차시 상태를 제공합니다. `enrollment-service`는 수강과 차시 진도를 소유하며 권한과 강의 상태를 동기 호출로 확인합니다. `payment-service`는 구독·결제와 Outbox를, `recommend-service`는 추천 요청과 결과를 소유합니다.

다른 서비스의 ID는 논리 참조로만 저장하고, 필요한 정보는 REST API나 Kafka 이벤트로 확인합니다.

## 슬라이드 19. 수강신청 동기 호출 흐름

[화면: 직원에서 enrollment·user·course-service로 이어지는 순서도]

수강신청은 권한과 데이터 정합성이 즉시 확정되어야 하므로 동기 REST로 처리합니다.

직원이 `POST /api/enrollments`로 강의 ID를 보내면 Gateway가 토큰을 검증하고 `enrollment-service`로 전달합니다. `enrollment-service`는 `user-service`에서 기업의 구독 권한이 ACTIVE인지 확인하고, `course-service`에서 강의가 ACTIVE인지 확인합니다. 두 검증을 통과한 후 중복 수강을 확인하고 수강 데이터를 생성합니다.

구독 비활성, 비활성 강의, 중복 수강, 내부 권한 조회 실패는 각각 다른 오류 상태로 구분해 반환합니다.

## 슬라이드 20. 결제·구독 Kafka 이벤트 흐름

[화면: payment-service Outbox에서 user-service 권한 반영까지]

반면 결제·구독 상태 변경은 Kafka 이벤트로 전파합니다.

`payment-service`는 멱등키로 중복 결제를 차단한 후, 구독 상태 변경과 같은 트랜잭션에 Outbox 이벤트를 저장합니다. 미발행 이벤트는 재시도를 거쳐 Kafka로 전달됩니다. `user-service`는 `eventId`를 기준으로 중복 수신을 차단한 후 이용 권한의 상태·좌석·기간을 갱신합니다.

발행 이벤트는 결제 성공·실패, 구독 해지·만료·갱신의 5종입니다. 해지할 때는 현재 이용 기간까지 ACTIVE 권한을 유지하고, 만료 이벤트에서 신규 가입과 수강신청을 차단합니다.

## 슬라이드 22. 핵심 API Request·Response

[화면: 수강신청·차시 완료·AI 추천 예시와 주요 오류 코드]

수강신청은 Access Token과 강의 ID를 `POST /api/enrollments`로 보냅니다. 정상 처리되면 `201 Created`와 함께 수강 ID, `ENROLLED` 상태, 0의 진도율을 반환합니다. 차시를 완료하면 서버가 진도율과 전체 수강 상태를 다시 계산해 반환합니다.

AI 추천은 `POST /api/courses/recommendations`로 다섯 가지 조건을 보내고, 추천 ID·출처·강의 정보·추천 이유를 받습니다.

예외도 계약으로 구분했습니다. 좌석 초과·중복 수강·중복 결제는 409, 구독·초대·강의 상태 문제는 422, 추천 서비스 처리 실패는 503으로 응답합니다.
